# v1.1.0 — Web-Based Bulk Import/Export for Graph Annotations (Excel + YAML)

**Epic:** Annotation throughput · **Depends on:** v1.0.0

## Context

This doc previously sketched a **CLI-only**, **Excel-only**, **create-only**
bulk importer. It has been expanded into a plan for **web-based** bulk
import *and* export of graph annotations (nodes + edges), in **both Excel
and YAML**, usable by the project **admin** and the document's **assigned
annotator** — and import must be able to **override existing annotations**
(update rows whose `node_id`/`edge_id` already exists on the graph), not
just create new ones.

This is a **design doc only** — no code lands with it. Three decisions were
confirmed before writing it (see below); everything else follows from those
plus the existing schema-driven architecture in `CLAUDE.md` ("The one
defining constraint": the importer must never hardcode a CAMO slot name —
column discovery, validation, and creation all route through
`SchemaView`/`bind_form_data`, exactly like the live annotation form and
the existing YAML exporter already do).

## Confirmed decisions

1. **Sync scope is a per-upload checkbox**, default off. Unchecked
   (default) = **upsert-only**: rows in the file create or update matching
   `node_id`/`edge_id`; anything already on the graph but absent from the
   file is left untouched. Checked = **full sync**: anything on the graph
   not present in the file is deleted via the existing `delete_node`/
   `delete_edge` service calls (audit still fires).
2. **Two-step flow, not immediate apply**: upload → server parses,
   validates, and diffs against current graph state → renders a per-row
   preview report with zero writes → user clicks **Apply** → second request
   commits. This protects a destructive "override" action with an explicit
   confirmation step.
3. **Reuse existing status/role policy, don't invent a new one**: admins
   bypass `Assignment` status entirely (may import into `reviewed`/`gold`
   edges); annotators may import only while their assignment is editable —
   identical to the rule `apps.annotation.policies.require_editable_assignment`
   already enforces for manual edits.

Origin marking stays as originally settled: every row an import creates or
updates is `origin=Node.ORIGIN_HUMAN` / `Edge.ORIGIN_HUMAN` — a human
choosing to bulk-load work, unrelated to the LLM proposal seam
(`apps/llm`, off by default, untouched by this feature).

## Why this is risky, briefly

Loom's core promise is schema-agnosticism plus an audit trail per
create/update. A naive importer (`pandas`/`openpyxl` → raw
`Node.objects.create()` or `bulk_create`) would bypass both — hardcoding
whatever columns today's CAMO version happens to have, and writing rows
with no `AuditEvent`. Allowing *updates* (override) raises the stakes
further: a bad upload can silently clobber another annotator's completed
work. Every design decision below exists to prevent that — the two-step
preview/apply flow, the diff report, and reusing the existing status/role
gates are the load-bearing safety mechanisms, not incidental UX.

## Formats

### YAML

Input shape is `serialize_graph()`'s output, unchanged, with `provenance`
and `source_document` ignored on import — this feature is scoped to nodes
+ edges only; a graph's bibliographic `source_document` already has its own
surface (`update_graph_source_document`):

```yaml
nodes:
  - node_id: node-a
    name: Buckthorn
    entity_type: shrub
    ...
edges:
  - edge_id: edge-1
    subject: node-a
    object: node-b
    predicate: positively_regulates
    ...
```

### Excel

Two-sheet workbook, schema-driven exactly like the original doc's
`export_import_template` sketch — but now also the *export* format, so
"download your annotations, edit them, re-upload" is a real round-trip for
both formats:

- **Nodes**: `node_id`, `name`, then one column per `slot_names("CausalNode")`.
- **Edges**: `edge_id`, `subject_node_id`, `object_node_id`, `predicate`,
  then one column per `slot_names("CausalEdge")`.

One writer function serves both the pre-filled export and the blank
template — `blank=True` skips data rows but keeps headers, so the template
always matches the project's pinned schema version:

```python
# apps/export/import_excel.py
def write_graph_xlsx(graph, *, blank: bool = False) -> bytes:
    """Two-sheet workbook (Nodes, Edges). Columns from slot_names(); data
    rows from serialize_graph(graph) unless blank=True (headers only)."""

def parse_xlsx_import(file_obj) -> tuple[list[dict], list[dict]]:
    """Read Nodes/Edges sheets -> (node_rows, edge_rows), each a
    header->cell dict. Blank rows skipped. Raises ImportParseError on
    missing/misnamed sheets."""
```

```python
# apps/export/import_yaml.py
def parse_yaml_import(file_obj) -> tuple[list[dict], list[dict]]:
    """yaml.safe_load -> (data.get("nodes", []), data.get("edges", [])).
    Ignores provenance/source_document. Raises ImportParseError on
    non-dict top level or non-list nodes/edges."""
```

Both readers hand off plain `node_rows`/`edge_rows` (flat dicts) to a
shared, format-agnostic diff/plan core — format-specific code never
touches `bind_form_data`, service calls, or diffing directly.

## Authorization

No existing helper combines "admin bypasses everything" with "annotator
needs an editable assignment." Add one next to what it composes:

```python
# apps/annotation/policies.py
def require_import_access(document, user) -> tuple[Assignment | None, bool]:
    """Return (assignment_or_None, is_admin). Admins/superusers bypass
    Assignment status entirely (may import into reviewed/gold edges);
    everyone else must hold an editable Assignment for this document —
    identical to the rule manual node/edge edits already enforce."""
    membership = ProjectMembership.objects.filter(
        project=document.project, user=user
    ).first()
    is_admin = user.is_superuser or (
        membership and membership.role == ProjectMembership.ROLE_ADMIN
    )
    if is_admin:
        return None, True
    return require_editable_assignment(document, user), False
```

`ImportUploadView`/`ImportPreviewView`/`ImportApplyView` all call
`require_import_access(graph.document, request.user)` first. `ExportExcelView`
and the existing `ExportGraphView`/`ValidateGraphView` keep the looser
`_require_access` (superuser or any project member) — read/export access
stays open to the whole project team; only import/write is gated by the
new helper. No per-edge-status check is added inside the service layer:
`update_edge` doesn't gate on `Edge.status` today and neither does the
manual edit view, so the importer doesn't invent one either — status
protection lives entirely in `require_import_access`.

## The preview/apply mechanic

**Server-side cache, keyed by a token embedded in the preview page's Apply
button, with a TTL** — not re-upload-and-trust. Re-posting the file on
Apply and re-parsing would require either round-tripping it back to the
browser as a hidden blob, or writing it to a temp location server-side
between requests — same "stash state between two requests" problem, worse
implementation, and it reopens the exact race the two-step flow exists to
prevent (the file changing between preview and apply).

```python
# apps/export/import_store.py
from django.core.cache import cache
import secrets

IMPORT_PLAN_CACHE_PREFIX = "graph-import-plan"
IMPORT_PLAN_TTL_SECONDS = settings.LOOM_IMPORT_PLAN_TTL_SECONDS  # _positive_env_int("LOOM_IMPORT_PLAN_TTL_MIN", 15) * 60

def stash_plan(plan: "ImportPlan") -> str:
    token = secrets.token_urlsafe(24)
    cache.set(f"{IMPORT_PLAN_CACHE_PREFIX}:{token}", plan, timeout=IMPORT_PLAN_TTL_SECONDS)
    return token

def load_plan(token: str) -> "ImportPlan | None":
    return cache.get(f"{IMPORT_PLAN_CACHE_PREFIX}:{token}")

def discard_plan(token: str) -> None:
    cache.delete(f"{IMPORT_PLAN_CACHE_PREFIX}:{token}")
```

`ImportPlan` is plain data (dicts/strings/ints, no live ORM instances) so
it's cheap and safe to pickle through whatever cache backend is configured
(`LocMemCache` in dev/test, `django_redis` in prod). `ImportPreviewView`
stamps `graph_id`/`uploaded_by_id` into the plan; `ImportApplyView`
re-checks both against the current request as defense in depth beyond the
token's own unguessability.

**Apply re-verifies, it doesn't blindly trust the cached verdict.**
`apply_import_plan()` re-resolves each `node_id`/`edge_id` against the
database at apply time and always goes through an idempotent
create-or-update path, rather than hard-asserting "this must still be a
CREATE." The cached `verdict` on each `RowResult` is authoritative for the
*preview display* the user approved, not for how the write executes — this
keeps Apply safe even if the plan is a few minutes stale.

**TTL and expiry**: default 15 minutes (`LOOM_IMPORT_PLAN_TTL_MIN`, same
`_positive_env_int` pattern as the `MAX_*_MB` settings). If Apply is
clicked after expiry, `load_plan()` returns `None` and `ImportApplyView`
re-renders the upload form with "your preview expired, please re-upload" —
no partial-apply risk.

## Row diff/report semantics

```python
# apps/export/graph_import.py
from dataclasses import dataclass, field
from typing import Any

VERDICT_CREATE = "create"
VERDICT_UPDATE = "update"
VERDICT_NOOP = "noop"
VERDICT_WOULD_DELETE = "would_delete"
VERDICT_ERROR = "error"

@dataclass
class RowResult:
    sheet: str                # "Nodes" | "Edges"
    row_number: int            # 1-based, sheet row or YAML list index
    id_value: str               # node_id or edge_id
    verdict: str
    bound_data: dict | None = None       # bind_form_data() output; None for NOOP/ERROR/WOULD_DELETE
    changed_fields: dict[str, tuple[Any, Any]] = field(default_factory=dict)  # UPDATE only
    errors: list[str] = field(default_factory=list)                          # ERROR only
    subject_node_id: str | None = None   # edges only
    object_node_id: str | None = None    # edges only

@dataclass
class ImportPlan:
    graph_id: int
    uploaded_by_id: int
    format: str                # "xlsx" | "yaml"
    full_sync: bool
    source_sha256: str
    node_results: list[RowResult]
    edge_results: list[RowResult]

    def counts(self) -> dict[str, int]:
        """{'nodes_create': n, 'nodes_update': n, ..., 'edges_error': n, ...}"""
```

Identifier/reference columns (`node_id`, `edge_id`, `subject_node_id`/
`object_node_id`) are stripped from each row before `bind_form_data` sees
it — the same managed-slots split the live form already performs, now
hoisted into `apps.annotation.services` so both `apps.annotation.views` and
`apps.export.graph_import` import one definition instead of two drifting
copies.

```python
def build_import_plan(graph, node_rows, edge_rows, *, schema_view, full_sync: bool,
                       source_sha256: str, format: str, uploaded_by_id: int) -> ImportPlan:
    """
    1. baseline = serialize_graph(graph); index by node_id / edge_id.
    2. For each node row: bind_form_data(schema_view, "CausalNode", row,
       excluded_slots=NODE_MANAGED_SLOTS). Binding errors -> ERROR row.
       Otherwise diff bound.data against baseline[node_id] (if present,
       ignoring the "annotator" key — see below) — equal -> NOOP, different
       -> UPDATE (changed_fields populated), absent from baseline -> CREATE.
    3. Build a resolved node_id set = baseline node_ids UNION node_ids
       CREATEd/UPDATEd/NOOP'd in this file (both existing and newly
       declared nodes are valid edge endpoints).
    4. For each edge row: same bind/diff against baseline[edge_id], plus
       resolve subject_node_id/object_node_id against the resolved set
       from step 3 -> ERROR if either endpoint is unresolvable.
    5. If full_sync: any baseline node_id/edge_id NOT touched by a row in
       this file -> WOULD_DELETE.
    6. Full-sync conflict check: an edge row that is CREATE/UPDATE/NOOP
       whose subject or object is itself WOULD_DELETE becomes ERROR
       instead — deleting that node would orphan the edge the file just
       asked to keep. Message: "subject/object node '<id>' is not present
       in this file and will be deleted under full sync; include it or
       remove this edge."
    """
```

**Diff comparison excludes the `annotator` field.** `_annotate_with_orcid()`
rewrites `data["annotator"]` to the *importing* actor's ORCID/username on
every create/update call regardless of what the row says, so comparing it
would make every re-run of an unchanged file report spurious UPDATEs.

**Node reference resolution** (original doc's open question #1, now
resolved): `subject_node_id`/`object_node_id` may match a node row
elsewhere in the same file, or a node already on the graph — both are
valid. This matters more with upsert-only as the default: most edge rows
in a typical "download, tweak two rows, re-upload" workflow reference
nodes that already exist and aren't repeated in the file.

**Partial-success semantics** (open question #2, resolved): row-level
`bind_form_data` errors block only that row — an ERROR row is never
written, the rest of the file still applies. Blocking a whole 200-row
import over one bad enum value in row 84 works against Loom's primary
audience (students annotating at speed). Whatever set of rows *is* applied
still commits inside one outer `transaction.atomic()` — partial row
selection, all-or-nothing per commit.

**Re-run idempotency** (open question #3, resolved by this feature):
upsert-by-`node_id`/`edge_id` is now the default, not a later follow-up.

### Report rendering

`render_plan_text(plan) -> str` produces the CLI's stdout report and is
reused, via the same `RowResult`/`ImportPlan` objects, as the template
context for `import_preview.html` — one source of truth for what a verdict
means, not two independently drifting renderers:

```
Row 2 (Nodes): would UPDATE node "Buckthorn" [node_id=node-a]
  entity_type: "shrub" -> "woody shrub"
Row 3 (Nodes): ERROR — entity_type: "shurb" is not a permissible value
Row 2 (Edges): would CREATE edge node-a --[positively_regulates]--> node-b
Row 3 (Edges): would DELETE edge "edge-9" (not present in file, full sync)

12 node rows: 8 create, 3 update, 1 error
8 edge rows: 6 create, 1 update, 1 delete (full sync)

Preview only — click Apply to commit, or re-upload to start over.
```

## Validation layering

1. **Per-cell/per-slot** — `bind_form_data()` (type coercion, enum
   membership, numeric bounds, patterns, required-ness), per row — same
   engine the live form uses.
2. **Whole-record LinkML pass (optional, after commit)** — running
   `validate_graph_data(serialize_graph(graph), schema_yaml)` after Apply
   and surfacing a link to `ValidateGraphView` ("N validation warnings
   remain on this graph") catches cross-field/whole-graph constraints
   `bind_form_data` doesn't check. Not blocking — a row that binds cleanly
   per-slot is still written even if the whole-graph pass would flag it,
   matching how manual annotation-form saves already behave (only export
   blocks on whole-graph validity today).

## Audit

Every create/update/delete during Apply fires the normal `emit_audit` call
via the existing service functions — no new audit code needed for
individual rows. Add one wrapping event so "was this graph bulk-imported"
doesn't require diffing hundreds of individual `node.update`/`edge.create`
entries:

```python
# apps/annotation/services.py
def emit_import_audit(actor, graph, *, format: str, full_sync: bool, counts: dict) -> None:
    emit_audit(
        actor, "graph.import", "CausalGraph", graph.pk,
        {"format": format, "full_sync": full_sync, **counts},
    )
```

Called once at the end of `apply_import_plan()`, after all per-row service
calls have emitted their own `.create`/`.update`/`.delete` events. No new
action-tag scheme for individual rows — the audit log reads identically
whether a row came from the form or an import; only the wrapping
`graph.import` event distinguishes "this was a bulk operation."

## CLI (secondary — thin wrapper, not a parallel implementation)

Both original CLI commands survive as optional admin-scripting surfaces,
calling the same `graph_import.py` core the web views use. A single
`manage.py` invocation is one process, so there's no preview/apply request
boundary to bridge — no cache token needed; `--apply` builds and
immediately applies the plan in one call:

```
python manage.py import_nodes_edges <graph_pk> file.xlsx|file.yaml [--full-sync] [--apply]
python manage.py export_import_template <graph_pk> -o template.xlsx   # thin wrapper around write_graph_xlsx(graph, blank=True)
```

Default (no `--apply`) prints `render_plan_text(build_import_plan(...))`
and writes nothing — the same dry-run/apply split as `migrate_graph`.

## Migration/versioning note

A file exported from one schema version, re-imported after the graph's
pinned `schema_version` has moved forward, is a real scenario (CAMO
evolves). This plan does not add migration logic to the importer — a
dropped slot simply produces a `_form`-level "field not defined by the
active schema" error on the affected rows via existing `bind_form_data`
behavior (per-row ERROR, not a crash). Building schema-migration
assistance into the importer would duplicate `migrate_graph`'s job; that
stays a separate, dedicated concern.

## Open questions

1. **Cache backend capacity for very large graphs.** A graph with several
   thousand nodes/edges could produce an `ImportPlan` large enough to be an
   awkward cache value (Redis `maxmemory` policy, `LocMemCache`'s lack of
   eviction limits in dev). No current test data approaches this, but a
   row-count ceiling (reject files past N rows with a clear error) should
   be decided before shipping, rather than discovered under load.
2. **Concurrent imports on the same graph.** Two admins previewing
   overlapping imports at once could each get a plan that no longer
   matches what actually lands by the time they click Apply (each
   individually re-verifies and upserts fine, but the *set* of changes
   either previewed may drift). Low likelihood given Loom's per-document
   assignment model, but the shipped feature should say explicitly
   "last Apply wins, no locking" rather than leave it implicit.
