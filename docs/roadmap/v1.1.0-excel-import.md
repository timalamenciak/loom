# v1.1.0 — Excel Import for Nodes and Edges

**Epic:** Annotation throughput · **Depends on:** v1.0.0

## Goal

Let an annotator bulk-create nodes and edges from a spreadsheet instead of
the one-at-a-time annotation form — useful when a project already has
structured causal data (e.g. transcribed from a prior spreadsheet-based
workflow) and re-keying it through the UI would be pure toil. This is a
**design doc only** — no code lands with it. It exists so implementation can
start from an agreed shape rather than improvised mid-build.

This doc is deliberately scoped against "The one defining constraint" in
`CLAUDE.md`: the importer must never hardcode a CAMO slot name. Column
discovery, validation, and creation all route through the same schema-driven
machinery the live annotation form already uses.

## Why bulk import is risky here, briefly

Loom's core promise is schema-agnosticism plus an audit trail per
create/update. A naive importer (raw `Node.objects.create()` off a `pandas`
DataFrame) would bypass both — it would hardcode whatever columns today's
CAMO version happens to have, and it would create rows with no `AuditEvent`.
Every design decision below exists to avoid that.

## Precedent to reuse, not reinvent

| Concern | Existing code to build on |
|---|---|
| CLI command shape | `apps/projects/management/commands/import_ris.py` — thin `BaseCommand`, delegates to a `services.py` function, maps `ValueError`/`DoesNotExist` to `CommandError` |
| Dry-run / diff-report UX | `apps/export/management/commands/migrate_graph.py` — `--report`-only mode, styled stdout sections, explicit verdict line |
| Column discovery (schema-driven) | `apps.schemas.schema_engine.get_schema_view(schema_version, project).slot_names("CausalNode" / "CausalEdge")` |
| Per-row type coercion + validation | `apps.schemas.input_binding.bind_form_data(schema_view, class_name, row_dict)` → `BindingResult(data, errors)` — same engine the live form uses |
| Whole-record LinkML check (optional final pass) | `apps.export.validators.validate_instance_data(data, schema_yaml, target_class=...)` |
| Row creation (audit + ontology pin + ORCID, for free) | `apps.annotation.services.create_node` / `create_edge` — never raw `.objects.create()` |
| Upload size/type gating | `apps/projects/upload_validation.py` pattern + `settings.MAX_*_UPLOAD_BYTES` |

## Proposed shape

### Command

```
python manage.py import_nodes_edges <project_id> <document_id> sheet.xlsx [--dry-run] [--sheet-name Nodes/Edges]
```

Two-phase like `migrate_graph`: run with `--dry-run` first to get a full
per-row report with zero writes, then re-run without it to commit. Both
passes use identical parsing/validation code so the dry-run report is a
reliable preview, not a best-effort guess.

### Template generation

Rather than document expected columns in prose (which drifts the moment
CAMO changes), add a companion command that **generates** the template from
the project's active schema:

```
python manage.py export_import_template <project_id> -o template.xlsx
```

Two sheets, built from `slot_names("CausalNode")` / `slot_names("CausalEdge")`:
- **Nodes**: `node_id`, `name`, plus one column per node slot the schema
  defines.
- **Edges**: `edge_id`, `subject_node_id`, `object_node_id`, `predicate`,
  plus one column per edge slot. `subject_node_id`/`object_node_id`
  reference the Nodes sheet's `node_id` column (same rules as CAMO's
  `subject`/`object` slots today).

This guarantees the template an annotator downloads always matches
whatever schema version their project is actually pinned to — no separate
doc to keep in sync.

### Validation and creation flow

For each row:
1. Map cells to a `form_data`-shaped dict keyed by slot name (the header
   row from the generated template already matches slot names 1:1).
2. Call `bind_form_data(schema_view, "CausalNode"/"CausalEdge", row_dict)`.
   Collect `.errors` per row instead of raising — one bad cell must not
   sink the whole file.
3. Node rows: resolve `subject_node_id`/`object_node_id` for edge rows
   against node_ids created earlier **in the same import batch** (see open
   question below) before calling `create_edge`.
4. Valid rows call `create_node`/`create_edge` inside one `transaction.atomic()`
   per invocation — audit events, ORCID annotation, and ontology-snapshot
   pinning all happen automatically, exactly like the annotation form.
5. Rows with binding errors are collected into a report, never written.

### Report format (mirrors `migrate_graph`'s style)

```
Row 2 (Nodes): would create node "Buckthorn" [node_id=node-a]
Row 3 (Nodes): ERROR — entity_type: "shurb" is not a permissible value
Row 2 (Edges): would create edge node-a --[positively_regulates]--> node-b
Row 3 (Edges): SKIPPED — edge_id "edge-1" already exists on this graph

12 node rows: 10 would create, 2 errors
8 edge rows: 7 would create, 1 skipped

Dry run only — re-run without --dry-run to commit.
```

### Dependency

`openpyxl` is currently only a **transitive** dependency (pulled in by
`linkml`, per `requirements.lock`). Add it as an explicit direct dependency
in `pyproject.toml` before relying on it — a future `linkml` release could
drop it without warning.

### Origin marking

Imported rows should almost certainly be `origin=Node.ORIGIN_HUMAN` — an
annotator choosing to bulk-import their own prior work is a human action,
distinct from the LLM proposal seam (`apps/llm`, off by default). Confirm
this with whoever scopes the implementation; it's a one-line decision but
worth stating explicitly since it's adjacent to that seam.

## Open questions to resolve before implementation

1. **Node reference resolution in the Edges sheet.** Does `subject_node_id`
   match only nodes created earlier in the same import run, or also
   existing nodes already on the graph? (Probably both — but state it.)
2. **Partial-success semantics.** If 8 of 20 rows are valid, does the
   importer commit the 8 and report the other 12, or is it all-or-nothing?
   `import_ris_file` today is effectively "create what you can, skip
   duplicates" — decide whether to match that or be stricter here given
   nodes/edges are higher-stakes than bibliographic records.
3. **Re-run idempotency.** If an annotator fixes 2 rows and re-runs the
   same file, should existing `node_id`s be upserted, or does every run
   always create new rows (relying on `unique_together = [("graph",
   "node_id")]` to reject duplicates)? Upsert is friendlier but is a bigger
   feature — flag as a possible v1.2 follow-up rather than building it into
   the first cut.
4. **Where does this live in the UI?** CLI-only (admin/staff run it on an
   annotator's behalf) vs. a web upload form under the project. CLI-only is
   the smaller first cut and matches `import_ris`'s current UX; a web form
   is a natural v1.2 follow-up once the CLI version is validated.
